title: How It Works
description: A short tour of the DocSync sync model

DocSync's job is to keep every client's document consistent without dictating how your documents are structured. It's a sync protocol, not a document library — the document library you plug in (DocNode, Yjs, Loro, custom OT, etc.) is what actually understands operations. DocSync's job is to assign them a single global order and shuttle them between clients.

## Vocabulary

Three concepts show up everywhere in the rest of the docs:

- **Snapshot (`serializedDoc`)** — the full state of a document at some point in time, ready to persist as a single blob.
- **Operation** — a change you can apply to a snapshot to produce a newer state.
- **Clock** — a monotonically increasing number. Every operation gets one when the server accepts it. Snapshots carry the clock of the most recent operation they include.

## The client

For each open document, the client keeps three things in memory:

1. **`serializedDoc`** — a snapshot at some `clock`, plus the **server batches** stored after it and not folded into it yet. Together they are the server's state at the clock of the last batch.
2. **`localOps`** — operations the user has made locally that the server hasn't confirmed yet.
3. **`doc`** — the "live" document the UI reads from. Conceptually equal to `serializedDoc` with `localOps` applied on top.

Every edit (a keystroke, a click, anything) follows the same path:

- The new operation is appended to `localOps`.
- `doc` is updated immediately so the UI re-renders right away — no round-trip required.
- A sync request is scheduled to push `localOps` to the server.

Pieces 1 and 2 are persisted (by default to IndexedDB), so closing the tab or going offline doesn't lose anything. Piece 3 is reconstructed from 1 + 2 on startup.

Storing a server batch appends it as is, so it costs as much as the batch, not as much as the document. The batches are folded into the snapshot when a subscription has something to reconcile (on load or after a reconnect, when the client sends local edits or receives batches it missed) and once 500 of them pile up during a long session. Loading reads the snapshot and applies the batches stored after it.

## Subscribing and receiving pushes

The first sync of a document on a connection **subscribes** to it. The client sends its `clock` and its `localOps` (and its snapshot only while its copy is still at clock `0`, because a document created on this client, for example offline, may not exist on the server yet); the server replies with what the client is missing since that clock (operations, or the snapshot when the log no longer reaches that far) and the clock assigned to the client's operations.

From then on, the server **pushes** every batch it saves for that document to every subscribed connection, in the order it saves them. A push carries only the document id and the operations: Socket.IO delivers messages of a connection in order, and the server numbers batches one by one, so each push is the batch after the previous one. Other tabs of the sending device get a bare notice instead, because they already have those operations. Later syncs from a subscribed client carry only `localOps`, and the reply is just their clock.

After a reconnect the client subscribes again from its stored clock, so it catches up on whatever it missed. If the server has lost its copy (for example, it expired), it saves nothing and asks for the snapshot, and the client repeats the subscription with it.

## Applying what arrives

### a) No concurrent edits

When the client has no unconfirmed operations, a pushed batch is applied to `doc` and appended to the stored server batches. When the server confirms the client's own operations, the client:

- Moves `localOps` to the stored server batches, with the clock the server gave them.
- Clears `localOps`.
- `doc` doesn't visibly change — the UI was already showing the same state.

### b) Concurrent edits from other clients

A batch from another client can arrive while the client still has `localOps` the server has not confirmed. The server puts that batch first, so the client:

- Starts from `serializedDoc` and its stored server batches.
- Applies the server's batch first.
- Applies `localOps` on top.
- Replaces `doc` with the result.

The UI re-renders to reflect the merged state.

This is what makes DocSync agnostic to the document library you choose: it guarantees that every client applies operations in the same total order — the order the server assigns. That's a stronger guarantee than what protocols like Hocuspocus give, which lean on CRDT-specific properties to converge. Because DocSync enforces order at the protocol level, it works equally well with CRDT libraries (where operations commute naturally) and with OT-style libraries (where the library handles re-application via transformation).

## The server

The server stores, per document:

- The latest **snapshot** (clock-tagged).
- An append-only **log of operation batches** since that snapshot, each tagged with its own clock.

When a subscription arrives with `clock = X`, the server:

1. Looks up operations with `clock > X` (what the client is missing).
2. Appends the client's incoming operations to the log, assigning them the next `clock`.
3. Replies with the missing operations (if any), the snapshot (only if the client has no copy or the snapshot is newer than the client's), and the assigned clock.

Every saved batch is then pushed to the other subscribers. The server handles the syncs of a document one at a time, from saving a batch to pushing it, so every connection receives the batches in clock order.

When the operation log gets long, the server squashes it into the snapshot and trims the log.

## Why a snapshot _and_ an operation log?

A simpler design would be to store just the latest snapshot and rewrite it on every operation. That's how [Hocuspocus's database extension](https://tiptap.dev/docs/hocuspocus/server/extensions/database) works — the provider exposes only `fetch` and `store`, and on every incoming change the server loads the document from storage, parses it, applies the operation, serializes the result, and writes it back.

That's a smaller provider surface, but it pays a parse + serialize round-trip on every edit. DocSync trades two extra methods (`saveOperations` and `deleteOperations`) for a much cheaper hot path:

- **Single-writer documents** — every edit is a single append to the operation log. No read, no parse, no rewrite of the snapshot.
- **Multiple concurrent writers** — clients exchange small operation deltas through the server, not full document snapshots. The server still just appends and replies with the missing range.
- **Squashing is rare** — the snapshot is only rebuilt when the log grows long enough to be worth it, not on every write.

The extra methods don't add much code, either. The reference Postgres provider above is well under 100 lines, and most production providers land in the same ballpark.

## Persistence and offline

The client's `serializedDoc` and `localOps` need to live somewhere. We ship [`indexedDBProvider`](./providers#indexeddb-provider) for the browser, which writes both to IndexedDB as local changes are flushed. With it plugged in:

- Reloads lose nothing.
- Offline edits accumulate in `localOps` and flush as soon as the connection comes back.
- Startup reads from disk, rebuilds `doc`, then syncs.

Both client and server use the same pluggable provider model — see [Providers](./providers) for the full interface and how to bring your own.
